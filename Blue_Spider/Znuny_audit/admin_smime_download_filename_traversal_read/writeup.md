## Summary

`AdminSMIME`'s certificate **Download** action passes the attacker-controlled `Filename`
straight into `"$CertPath/$Filename"` and reads it with `Main::FileRead`, with no
canonicalisation or confinement. `Filename=../../../../../etc/passwd` therefore returns the raw
bytes of `/etc/passwd` as a file download. Unlike the sibling Delete action, the Download
branch performs **no `ChallengeTokenCheck`**, so it is also reachable via CSRF. Confirmed live:
the exploit downloaded verbatim `/etc/passwd` and `Kernel/Config.pm` (which contains the MySQL
credentials).

## How it works (mechanism & code trace)

**Entry point** — `Kernel/Modules/AdminSMIME.pm:360`, `Subaction=Download`:

```perl
360:  elsif ( $Self->{Subaction} eq 'Download' ) {
361:      my $Filename = $ParamObject->GetParam( Param => 'Filename' ) || '';
363:      my $Type = $ParamObject->GetParam( Param => 'Type' ) || '';
...
382:      else {                                           # Type ne 'key'
383:          $Download = $SMIMEObject->CertificateGet( Filename => $Filename );
384:      }
386:      return $LayoutObject->Attachment(
387:          ContentType => 'text/plain', Content => $Download,
388:          Filename => $Hash . '-' . $Type . '.pem', Type => 'attachment' );
```

Note there is **no `ChallengeTokenCheck`** anywhere in this branch (contrast the Delete branch,
`:116`, which calls `$LayoutObject->ChallengeTokenCheck();`).

**Sink** — `Kernel/System/Crypt/SMIME.pm`, `CertificateGet`:

```perl
1281:  my $File           = "$Self->{CertPath}/$Param{Filename}";
1282:  my $CertificateRef = $Kernel::OM->Get('Kernel::System::Main')->FileRead( Location => $File );
1284:  return if !$CertificateRef;
1285:  return $$CertificateRef;
```

`$Param{Filename}` is concatenated with **no** `FilenameCleanUp`, no `abs_path`, no check that
the result stays inside `$Self->{CertPath}`. `Main::FileRead` opens exactly that path.

**The exact defect.** The value that should be a bare certificate hash filename (e.g.
`a1b2c3d4.0`) is instead a fully attacker-chosen relative path. With `CertPath` at
`/opt/znuny/var/tmp/smc_*`, `Filename=../../../../../etc/passwd` resolves to `/etc/passwd`;
the returned scalar is streamed back as an attachment, disclosing the full byte content — not
merely existence.

**Why nothing else saves it.** `Layout::Attachment` streams whatever content it is given.
There is no allowlist of on-disk certificate hashes, no suffix constraint, and the CSRF token
that guards the Delete/Add branches is simply absent from Download.

## Why it is a vulnerability

The Download action is meant to export a *certificate the admin already imported into
`CertPath`* — its intended read scope is that one directory. Reading `/etc/passwd`,
`/opt/znuny/Kernel/Config.pm`, private keys, or any other host file violates the
application→host trust boundary (`S:C`): the admin frontend is authorised to manage Znuny's
S/MIME store, not to read arbitrary OS files.

That the *content* is returned (not just an existence signal) makes this strictly stronger than
VULN-007: `Kernel/Config.pm` disclosure hands the attacker the database credentials directly.
The missing CSRF token compounds it — a logged-in admin who loads an attacker page can be made
to fetch and exfiltrate host files without intending to. This is not a documented capability:
Znuny confines the *Add* path and tokenises *Delete*, showing the developers did not intend an
unconfined, tokenless read here.

## Reproduction

1. As admin, enable S/MIME (`SMIME=1`, `SMIME::Bin=/usr/bin/openssl`, and a writable
   `SMIME::CertPath` / `SMIME::PrivatePath`) — the exploit does this via SysConfig, deployed
   once (running workers pick it up without an Apache restart).
2. Issue a **tokenless** GET:
   ```
   GET /znuny/index.pl?Action=AdminSMIME;Subaction=Download;Type=cert;Filename=../../../../../etc/passwd
   ```
3. Run `./run.sh`. Expected proof lines:
   ```
   [PROOF] /etc/passwd: first line -> 'root:x:0:0:root:/root:/bin/bash'
   [PROOF] Kernel/Config.pm (DB creds): first line -> '# Generated by the cvehunter Znuny lab entrypoint.'
   [OK] exploit confirmed ...
   ```
Full capture: `request.http`, `response.txt`, `run.log`.

## Impact

- **Full-content arbitrary host file read** as an admin operator: DB credentials
  (`Kernel/Config.pm`), private keys, `/etc/passwd`, other apps' secrets — anything readable by
  `www-data`. DB creds → direct database compromise (all tickets, all customer PII, password
  hashes → VULN-030).
- **CSRF-forgeable** (no token, works as a GET), so a logged-in admin can be coerced by a
  malicious page into exfiltrating a targeted file.
- **Delete primitive:** the Delete branch runs `unlink "$CertPath/$Filename"` on the same
  unconfined `Filename` (`SMIME.pm:1360`), letting an admin remove arbitrary web-user-writable
  files (integrity/availability). Not exercised dynamically to avoid host damage.
- Chains with VULN-007/025/027/028 (host recon/SSRF) and VULN-041 (cleartext mail creds).

## Suggested fix

At `Crypt/SMIME.pm:1281` (and the `unlink` at :1360), confine before touching the FS:

```perl
use Cwd qw(abs_path);
$Param{Filename} = $Kernel::OM->Get('Kernel::System::Main')
    ->FilenameCleanUp( Filename => $Param{Filename}, Type => 'Local' );
my $Full = abs_path("$Self->{CertPath}/$Param{Filename}") // '';
return if $Full !~ m{^\Q$Self->{CertPath}\E/};   # must stay inside CertPath
```

And add `$LayoutObject->ChallengeTokenCheck();` to the `Download` branch in `AdminSMIME.pm:360`.
Principle: canonicalise-and-confine (allowlist the directory), and protect every state/asset
action with the anti-CSRF token, not just some.
